## When to Use
Use when the user asks to review a GitHub pull request (URL or PR number), especially one that already has review comments and where duplicating existing feedback must be avoided. Not for fixing failing CI on a PR (use fixing-pr-checks) and not for working through feedback on your own branch (use resolve-pr-comments).

## Procedure
1. Fetch PR context: `gh pr view N --json title,body,state,author,headRefName,headRefOid,baseRefName,url,reviews,files` — note the head ref name and OID (the commit_id every review comment must reference), and scan the body, particularly the NOT DONE / out-of-scope section (deferred dependencies are a prime source of review findings).
2. Build the existing-comment ledger BEFORE forming opinions: `gh api repos/O/R/pulls/N/comments --jq '.[] | {id, user: .user.login, path, line, body}'` — this covers every inline review comment including bot/Copilot findings. Also run `gh pr view N --comments` for top-level conversation and review summary bodies, since blocking issues are often stated there rather than inline.
3. Save and read the full diff: `gh pr diff N > /tmp/prN.diff`, then read it completely — every hunk, including comment-only changes (a deleted caveat is a finding in itself).
4. If repo-wide verification is needed (cross-file consistency, stale references, config drift), check out the PR head in a TEMPORARY worktree, never the main checkout: `git fetch origin <headRefName> && git worktree add /tmp/prN-review FETCH_HEAD`. Do all exploration there; `git worktree remove /tmp/prN-review` when finished.
5. Verify independently: cross-check values across files (rg for IDs/config/flags on the PR head), confirm each existing comment's claim is accurate, and hunt for gaps the existing comments missed — stale references in files the PR does NOT touch, caveats deleted while their dependency is still open (cross-reference the PR body's deferrals), and inconsistencies between docs, tests, and shipping config.
6. Deduplicate semantically, not just by path/line: reviewers anchor comments at the nearest changed line, so a finding can be flagged far from where it lives. For each candidate finding, check the ledger; drop or merge anything already raised, and keep only genuinely new items. Prepare a short agreement/disagreement note for each existing comment to include in the user-facing summary.
7. Anchor each new finding to a line that IS in the diff (GitHub rejects inline comments on unchanged files/lines — if the real location is untouched, anchor at the nearest related changed line and say so in the comment body). Verify each anchor against the actual head SHA before posting: `git show <headSha>:<path> | sed -n 'N,Mp' | cat -n` — line numbers in the diff output and in your memory drift.
8. Present the review to the user: overall verdict (APPROVE or REQUEST_CHANGES and why), a table agreeing/disagreeing with each existing comment, the new findings with proposed anchor lines and exact comment text. Wait for explicit approval before posting — comments land publicly under the gh-authenticated account (usually the user's own).
9. Decide the verdict, then submit ONE formal review (never loose standalone comments) so the author can track requested changes and see merge-readiness in the PR's review status:
   - Classify each new finding as BLOCKING (bug, regression, security/data-loss, broken test/CI, missing required behavior, contradicts PR intent) or NON-BLOCKING (nit, style, optional suggestion — prefix the comment "nit:" / "optional:").
   - Any BLOCKING finding, or any pre-existing human thread you confirmed is a valid unresolved blocker => event REQUEST_CHANGES. Otherwise => event APPROVE (non-blocking nits do not withhold approval). Use COMMENT only if the user/caller explicitly says so, or if you genuinely cannot reach a verdict (state why in the body).
   - GitHub rejects APPROVE/REQUEST_CHANGES on your own PR (and REQUEST_CHANGES with an empty body); on own PRs fall back to COMMENT.
   - The review body MUST start with a verdict emoji on its first line: 🟢 for APPROVE (e.g. "🟢 Approved") or 🔧 for REQUEST_CHANGES (e.g. "🔧 Changes requested"). Use no emoji verdict for the COMMENT fallback.
   - The review body is required, written TO THE PR AUTHOR, and SHORT: the emoji verdict line, then only what they must act on. Hard limits: at most ~100 words; REQUEST_CHANGES = a numbered "Must fix" list (one line each, pointing to the inline comment or path:line); APPROVE = one sentence at most (optional nits as a short list). Put detail in the inline comments, not the body.
   - Write for the author, never for the user or the agent. The body and every inline comment must contain NONE of: a report of what you verified/ran/checked ("tests pass", "verified in a worktree", "builds clean", "CI green"); a recap of earlier rounds or of threads that are now fixed ("earlier requested changes now resolved", "every earlier item addressed"); references to the ledger, dedupe, other comments being "complementary" or "no overlap", the sweep, the worktree, or the process; praise/filler ("looks good overall", "nice work"); restating the PR description. Those belong only in your private report back to the user (step 8), never in the posted review.
   - Inline comments: one problem per comment, 1-3 sentences, say what is wrong and the fix. Skip nits that don't change behavior unless trivially useful, and cap non-blocking items at ~3 per review.
   - Write the payload to a JSON file (never build markdown bodies with -f/-F shell quoting): {"commit_id": "<headSha>", "event": "APPROVE|REQUEST_CHANGES", "body": "<summary>", "comments": [{"path": ..., "line": N, "side": "RIGHT", "body": ...}]}. `comments` may be empty for APPROVE. Post with `gh api repos/O/R/pulls/N/reviews --input /tmp/prN-review-payload.json`.
10. Verify the post: re-fetch `gh api repos/O/R/pulls/N/comments` filtered to your login (`gh api user --jq .login`) and confirm each comment sits on the intended path/line. Report the review HTML URL to the user and clean up the payload file and worktree.
## Pitfalls
- The reviews API's `position` field is deprecated — use `line` + `side`. Added lines: side RIGHT with the head-version line number; deleted lines: side LEFT with the BASE-version line number.
- If the reviews endpoint rejects the anchor, fall back to standalone inline comments: POST `repos/O/R/pulls/N/comments` with the same {path, line, side, body} shape (plus commit_id). Less tidy (no grouping body) but works.
- If the author pushes a new commit after you fetched, your commit_id and line anchors are stale — re-fetch the head SHA immediately before posting and re-verify every anchor; a review submitted against a superseded commit confuses the thread.
- Keyword greps miss value-only staleness: e.g. files hardcoding an old client ID contain no word like 'borrow', so `grep -ri borrow` finds nothing while six test fixtures carry the retired value. Grep for the VALUES being replaced, not just the narrative words.
- Scanner-bot comments (Checkmarx et al.) frequently flag line-number drift on byte-identical pre-existing code as 'new' issues — do not mirror that noise into your review; diff the flagged line against the base ref first.
- The verdict must be a real signal: authors track REQUEST_CHANGES as their to-do list and APPROVE as "good to merge". Never post COMMENT when a verdict is reachable, never REQUEST_CHANGES for nits alone, and never APPROVE with an open blocker (including one a human already raised that is still unaddressed).
- If you previously requested changes on this PR and the author has fixed them, the new review must be APPROVE (that is what clears the block); re-verify each earlier blocker against the new head before approving.
- Copilot-style bot reviews often get the mechanism wrong while individual humans get specifics right (or vice versa) — verify each claim against the code instead of trusting the severity labels, and say in your summary which existing comments you confirmed vs. found inaccurate.

- Posted review text is public and read by the author. Process narration, verification logs and "earlier items resolved" summaries are bloat that reads as the agent talking to the user; GitHub already marks resolved threads and re-requested changes, so do not restate them.

## Verification
0. The posted body is under ~100 words, opens with 🟢/🔧, and contains none of the banned content from step 9.
1. The API response to the reviews call returns state APPROVED or CHANGES_REQUESTED (matching the findings: blocking => CHANGES_REQUESTED, otherwise APPROVED) with an html_url, and that URL renders the review on the PR page under the user's account.
2. Re-fetching the PR's comments shows each newly posted comment at exactly the intended path and line, with no comment restating an item already in the pre-existing ledger.
3. The temp worktree and payload file are cleaned up, and the main checkout is untouched (no stray branches, no modified files).
