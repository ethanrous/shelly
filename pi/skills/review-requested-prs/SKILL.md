## When to Use
When the user wants every pending review request handled in one shot: each open PR anywhere in their repos where they are an EXPLICIT, current reviewer (their login must appear in the PR's live `reviewers` list — the search index alone is not enough) gets its own subagent that reviews it and submits a formal APPROVE or REQUEST_CHANGES review under the user's account. PRs the search returns but where the user is no longer / was never an explicit reviewer (stale entries, team- or rule-based assignments) are skipped and reported, never reviewed. NOT for interactively reviewing a single named PR (use reviewing-github-prs directly). Requires gh auth; every relevant repo lives under ~/repos/.

## Procedure
1. Preflight: `gh auth status` must succeed. All repos live in ~/repos/ — if a queued PR's repo is missing there, clone it into ~/repos first (the user keeps every repo there); if the clone fails, skip that PR and note it in the final report.
2. Find the queue in ONE call: `gh search prs --review-requested "@me" --archived=false --state open --json number,title,url,repository,updatedAt,author` (headRefName/baseRefName are NOT valid search fields — get them from the per-PR probe below). Drop rows where author == the user (shouldn't occur; cheap guard). Also drop any row whose repo is archived/deprecated: run `gh repo view OWNER/NAME --json isArchived -q .isArchived` per distinct repo (the search flag is not reliable) and silently exclude archived repos — never surface or list them, not even as skipped. Treat the remaining list as CANDIDATES only — the per-PR probe in the next step decides what is dispatched. Sort by updatedAt ascending so the longest-waiting PRs dispatch first.
3. Per candidate PR, run ONE GraphQL probe that validates state, confirms the user is still an explicit reviewer, and supplies refs (parse OWNER/NAME from the PR url): `gh api graphql -f query='query($owner:String!,$repo:String!,$n:Int!){repository(owner:$owner,name:$repo){pullRequest(number:$n){state headRefName baseRefName headRefOid reviewRequests(first:20){nodes{requestedReviewer{... on User{login} ... on Team{name}}}}}}}' -F owner=$OWNER -F repo=$NAME -F n=$N`. Dispatch ONLY PRs that are state OPEN AND whose `reviewRequests` contain the user's login as a User (team entries do not count). `gh search prs --review-requested` is not authoritative — it can carry stale entries and team/rule-based assignments the user no longer sits on. Skip every non-qualifying row and report it with the reason (closed mid-sweep, user not an explicit reviewer).
4. Show the user the queue (repo, PR #, title, author, how long it has waited, plus which candidates were skipped and why), then spawn one subagent per dispatched PR — ALL Agent calls in a single message, every one run_in_background:true. Use sonnet-5.5 subagents with xhigh thinking for all dispatches — user preference for this sweep: reviews post publicly under the user's account, so quality outranks cost. Tell each subagent explicitly not to delegate further. Collision guard: if two queued PRs in the SAME repo share a headRefName they would land on the same worktree path — serialize those (spawn one, spawn the next upon its completion).
5. Each subagent prompt must be self-contained (fresh context). Include: repo path `~/repos/{repo}`; PR number, URL, author, headRefName, baseRefName, headRefOid; and this contract verbatim: (a) 'Perform a full code review of this PR and post it. Read the reviewing-github-prs skill first and follow it end to end, including the posting steps (its steps 8-10). Its interactive "wait for approval" step does NOT apply here — the user invoked this sweep as standing approval to post the review under their account. Do not pause to ask.' (b) 'Verify against a worktree, NEVER the main checkout: `git fetch origin {headRefName} && git worktree add ~/.worktrees/{repo}/{headRefName} FETCH_HEAD`. Do all exploration there; `git worktree remove` it when finished.' (c) 'Submit ONE formal review with a clear verdict, per steps 9-10 of the inner skill: REQUEST_CHANGES if there is any blocking finding (with a "Must fix before merge" list in the body), otherwise APPROVE. Nits alone never block. Keep the posted review short and addressed to the author: no verification logs, no recap of earlier rounds or resolved threads, no process talk — those go only in your return report to the user. The review body must open with 🟢 (APPROVE) or 🔧 (REQUEST_CHANGES), per step 9. Do not post loose comments, and do not use COMMENT unless it is the user\'s own PR (GitHub forbids self-review verdicts).' (d) Return: overall verdict, agree/disagree table for each pre-existing comment, the list of findings posted (path:line + gist), the review HTML URL, and confirmation the worktree was removed.
6. On each completion notification (never poll): verify — `gh pr view {n} --json reviews` shows an APPROVED or CHANGES_REQUESTED review by the user's login anchored at the current head SHA; if the author pushed between the subagent's fetch and its post, confirm the subagent re-anchored, otherwise flag it. Resume dead subagents or finish the review yourself; remove any leftover worktree under ~/.worktrees/{repo}/.
7. Final digest: one block per reviewed PR (verdict, top findings, review URL) plus a failures section (clone failures, PRs closed mid-run, candidates skipped because the user was not an explicit reviewer, API errors).
## Pitfalls
- Posts are public and permanent under the user's account — the inner skill's ledger-first dedupe step is the primary defense against the #1 auto-review failure: restating feedback a human already raised. Subagents must not shortcut its steps 1-3 (PR context, existing-comment ledger, full diff read) to save tokens.
- Always post a formal verdict: authors rely on CHANGES_REQUESTED to track what must change and on APPROVED to know they can merge. Comment-only reviews and loose comments leave them with no status. Blocking => REQUEST_CHANGES; only nits or nothing => APPROVE. Never manufacture blockers, and never approve over an unresolved blocker.
- `--review-requested "@me"` over-matches: the search index lags removals and surfaces team/branch-rule based assignments even for PRs the user was never explicitly added to (real case: ansible_infra and aws-automation PRs appeared in the queue though the user was not a reviewer on them and had to stop the agents mid-run). The per-PR `reviewers` list from the GraphQL probe is the source truth — if the user's login is not in it, do not dispatch, even though search returned the PR.
- The inner skill defaults to a /tmp/prN-review worktree; override it to ~/.worktrees/{repo}/{headRefName}/ per the user's convention. Clean it up whichever location was used.
- Review-requested != actionable: people add reviewers reflexively. A short, honest 'looks good, one minor nit' review is correct; never manufacture findings to seem thorough.
- Main checkouts in ~/repos stay pristine — all exploration happens in the worktree, no branches created in the main checkout.
- Scanner-bot noise (Checkmarx et al.) flagging line-number drift on byte-identical pre-existing code — the inner skill covers it; do not mirror that noise into the posted review.

## Verification
1. Every candidate NOT in the user's live `reviewers` list was skipped (no worktree created, no subagent spawned, no review posted) and appears in the final report with the skip reason.
2. For every dispatched PR, `gh pr view {n} --json reviews` includes an APPROVED or CHANGES_REQUESTED review (state matches the findings) by the user's login created during this run, anchored at the then-current head SHA.
3. Spot-check posted comments via `gh api repos/O/R/pulls/N/comments` filtered to the user's login: each sits at the intended path/line and none restates an item from the pre-existing ledger.
4. `git worktree list` in each affected repo shows no leftover worktrees under ~/.worktrees for processed PRs, and the main checkouts are untouched (no stray branches, no modified files).
5. The user received the per-PR digest with review URLs and the failures section.
